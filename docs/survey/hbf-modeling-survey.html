FlashLabAE / HBFSim 面向 OCP HBF v0.7.0 的开源 HBF 系统级性能模拟器 —— 简介、语言栈、SystemC 接入可行性与框架结构

语言 C++20（核心）+ Python 3.10+（前门） 许可 MIT 规格基准 OCP HBF v0.7.0（2026-08-03） 构建 CMake ≥ 3.20（Ninja 可选） SystemC 依赖：无 可作为库 hbfsim_core 嵌入

1. 它是什么

一句话：HBFSim 是一个因果（causal）的事件驱动内存系统模拟器，把 HBM、HBF（按 OCP HBF v0.7.0 建模）、两者之间的链路、以及外部 backing 存储，放进同一个仿真系统里，同时给出时序、容量、放置、数据搬运、映射、GC、写放大与寿命。

它建模什么

  • HBF 设备内部结构：独立通道、命令/收/发三条日历，raw channel、ECC、TSV、decoded SRAM、page buffer 各自有限的带宽日历
  • NAND 介质：4 KiB 页、每 bank 两个 decoded 页槽（LRU）、每 block 的 program-order 与 P/E 计数、page-0 自动擦除
  • 主机侧：host-managed FTL（全驻留 / 缓存 / block / 压缩策略）、写缓冲、GC、磨损均衡、zone 管理、持久化镜像
  • 物理约束：UCIe/AXI 接口带宽（Grade 1/2/3）、封装热模型（OCP §9.1–9.2 四档热节流）

它不做什么（明确边界）

  • 不是电气级 / flit 级模型：无 UCIe CRC、无 packet framing、无重放
  • 无 scratchpad SRAM 写路径、无 batch-read sense-round、无 per-AXI-ID 响应队列
  • 不做完整协议一致性验证（它是性能模型，不是 UVM/DUT）
  • 不含设备端 GC / copyback（按 OCP §11.4 由主机负责）
  • 不做 GPU 指令级仿真（那是 SlugLab/HBFSim 和 Accel-Sim 路线的分工）

3. 框架结构图

三个关键设计点

  • 前门不建模：python3 -m hbfsim 只负责编译、找配置、把事务喂给 build/hbfsim；每个结果目录都记录真实命令行，方便复现。
  • 主机与物理解耦：HbfController = 主机管理 + 物理流水线；HbfDevice 只有通道传输、program-order、完成可见性与 decoded 页缓存，不含 L2P / 分配器 / GC。所以你可以只取物理层。
  • 证据驱动：configs/parameter-provenance.json 记录每个物理参数的出处与证据等级；规范里 96/192 与 94/188 GB/s 的冲突被显式保留为未决项，而不是悄悄选一个。

4. 设备内部结构：层次与数据通路

HBFSim 对 HBF 的"结构"建模可以概括成一句话：层次是"Stack → Channel → Die → Plane/Bank → Block → Page"，而每一层都挂着一到数条有限带宽的"日历"——请求沿层次下行，每一级都在自己的日历上排队，总延迟就是各级 start/finish 串起来的结果。

4.4 结构图上"没有"的部分

看结构图时容易默认这些能力存在，实际都没有建模：scratchpad SRAM（规范里的可选特性）、batch-read sense 合并（多请求共用一次 tR）、per-AXI-ID 响应队列、UCIe flit / CRC / packet framing。做带宽与页级延迟评估够用；如果要做接口协议一致性或 scratchpad 场景，需要自己补。

5. 与 OCP HBF v0.7.0 的差距审计

第 4 节是按实现画的结构；这一节是按规范逐条对的差距。依据三处：规范原文（附页码）、模型自述边界（docs/reference/model.md）、以及对源码的全文检索实证。

影响等级：高 会改变带宽/延迟结论　中 影响特定场景或尾部行为　低 主要影响协议完整性/寿命研究

5.1 对外接口（UCIe / AXI）

#规范要求HBFSim 现状影响
A1Sideband 链路：SB 初始化、链路训练、参数交换、lane repair、带内寄存器访问（p.25-28, 63-65）未建模（sideband 全仓库 0 命中）低
A2Flit 层：Format 6 / Latency-Optimized 256B flit、packet type 与 opcode 编码（p.26-28, 78）只有"字节数 ÷ 带宽"，无 flit 打包/解包低
A3CRC、replay/重传、链路错误信令（p.62, 73, 101-104）未建模（模型自述："UCIe CRC/replay and packet framing are not implemented"）中
A4链路初始化四阶段、retimer（p.28）未建模低
A5每 UCIe 通道可配 1/2/4 个虚拟 AXI 接口，容量均分，主机自选交错（p.16, 23, 29-37, Figure 5）无 AXI 端口层：一条通道等效一条带宽中
A6AXI user 字段语义：ARUSER[2]=Batch Read、ARUSER[8:6]=Read Retry Stage、RUSER/BUSER[5:2]=CMD Status、[8:6]=ErrorInfo（p.41-42）事务只区分 HBF_LOGICAL / HBF_PHYSICAL / HBM / … 目标，无 user 字段与状态码映射中
A7同 AXI ID 保序、异 ID 可乱序（p.42 Note 1, p.57 #5）无 per-AXI-ID 响应队列（模型自述）高

5.2 地址映射与 DLU

#规范要求HBFSim 现状影响
B1本地地址低 4 bit = bank、次 2 bit = die（p.22）位序相反：bank = ppn / (blocks × pages)，bank 在高位、按容量整块划分（bank-major），不是规范的交错布局高
B24 AXI 端口 × 4KiB 交错的四种选项（p.23-24, Figure 5）未建模中
B3Device Logical Unit（64B）与 p.62-63 的失败重放地址计算（R1–R5 公式）无 DLU 概念（DLU 0 命中）；写累积走 ZONE_WRITE_BATCH 的 4 KiB 缓冲中

5.3 读路径

#规范要求HBFSim 现状影响
C1Batch read hint：带 hint 的读不等定时器，遇到 regular read 才成批下发（p.57-58）未建模（batch_read 0 命中；模型自述 "no batch sense-round mode"）高
C264B 粒度读、64 条命令凑 4 KiB、不跨页（p.56）已覆盖：64B–4KiB、按页 sense、后续命中走 decoded cache已实现
C3每 bank 两个 cache buffer、命中立即返回、第三页才驱逐（p.57 #7-8）已实现（2 槽 LRU，含 in-flight 填充可见性）已实现
C4读错误码：Invalid Address 0x1 / Temporary 0x2 / UECC 0x4 / CECC 0x5、Read Count 阈值（p.59-61）无 UECC/CECC 判定（uecc、correctable 0 命中），只有 erased/unmapped 错误中
C5读失败重试：base die 可配重试，或主机重试（p.57 #9）未建模（read_retry 0 命中）中
C6每 block 读计数用于 refresh 指示（p.19, 59, 118）未建模（模型自述 "disturb counters … are outside this transaction model"）低

5.4 写路径

#规范要求HBFSim 现状影响
D1非 posted、4 KiB 累加、首 64B 到达后限时收齐否则报错（p.58 #1-3,6）已实现（累积 + 超时 + 重复/超额拒绝）已实现
D24 KiB 本地地址不可跳过/跳跃；block 内顺序编程（p.58 #4,9）已实现（append-only，跳页报错），错误码不按规范枚举低
D3混合读写：读命中已累积部分返回数据，命中 pending 部分返回 0xA（p.59）部分实现：有 buffered_write_read_status 转发路径，但 0xA 语义未按规范建模中
D4程序失败 → 整 block replay（0x7），按 p.62-63 算 page-0 地址有 replay 机制，但地址计算用模型自己的映射，非规范 R1–R5中
D5退役容量（0x8，粒度 block/bank/die/channel，p.62, 121）有退役实现（retirement / validity 位），但没有错误码到主机的路径中
D6多平面编程 / cache program / suspend-resume（p.16 features 与厂商 datasheet）未建模（multi_plane、cache_program 0 命中）高

5.5 Scratchpad（规范可选特性）

#规范要求HBFSim 现状影响
E1每通道可选 scratchpad SRAM，高优先级读写、64B 粒度、L3 级延迟、掉电失效、主机自管（p.16, 57-58, 66, 74）完全未实现（模型自述 "scratchpad SRAM writes … not implemented"）高

5.6 介质可靠性 / 寿命

#规范要求HBFSim 现状影响
F1Bad block / 备用块管理、TSV 冗余与修复（p.19, 88）未建模（bad_block、redundancy 0 命中）低
F2Retention 失效（85 °C 24 h）、read disturb、MAXPEC 限制（p.106, 118, 129）未建模（模型自述排除）；PEC 计数本身有，作为磨损基线低
F3ECC 编解码已实现：raw 带宽 + 响应延迟 + 编解码共用发起端口已实现
F4禁止设备端 GC / copyback（p.117 §11.4）遵守：GC、磨损、zone 全在主机侧已实现

5.7 控制 / 调试 / 热

#规范要求HBFSim 现状影响
G1CSR/ADMIN 命令集：Set/Get Feature、Secure Erase、Get Log Page、BIST、Zone Remap、Read UCIe Errors、Reduced Capacity、Register R/W（p.43）只实现 Zone Remap，其余无中
G2设备状态寄存器（SPR / CSR / ISR、Immediate Readiness）、MMIO MAP（p.66）未建模（模型自述 "Register access … not modeled"）低
G3IEEE 1500 / DA Port / JTAG 三个测试接口（p.86-89）未建模；温度只"假定可经 IEEE 1500 读出"低
G4四档热节流 + 温度传感器（p.106-108）已实现热节流；但 9-bit 传感器编码、halt 期间维护命令、0x9 错误码、链路错误信令未建模（模型自述）中
G5上电时序、复位时序（p.82-83）未建模低

5.8 参数不确定性（规范本身的空洞，不是模型缺陷）

  • tR / tPROG / tERS 被规范明确推给厂商 datasheet（p.16）。模型用 4 µs / 75 µs / 2 ms 假设，并写入 configs/parameter-provenance.json 标注为证据不足。
  • 带宽数字自相矛盾：Table 2/4 写 96 / 192 GB/s，p.32/35 写 94 / 188 GB/s。模型选 p.16 并把冲突保留为未决项。
  • 几何与带宽不自洽：按规范"每通道 16 banks + tR=4 µs"只能得到 16.4 GB/s/通道，三种 Grade 都够不到；要成立必须假设每通道 47/94/188 个并行 sense，或 tR ≈ 1.37/0.68/0.34 µs（见第 8 节实测）。

5.9 如果要补齐，优先级怎么排

按"对结论的影响"排序，而不是按规范章节顺序：

  1. B1 地址位序 —— 已实现（commit 119c93a）并已量化：顺序物理读快 15.8×、写快 16×（见 8.1）；
  2. D6 cache program + 多平面 —— 多平面并行在模型里已经生效（关掉自动擦除后 64 页写 4.7 µs/页 = 75 µs ÷ 16），缺的是 cache program；
  3. C1 batch read —— 规范给了明确语义（ARUSER[2]），带提示的批量读现在会被高估；
  4. E1 scratchpad —— 规范里唯一的 L3 级低延迟路径，完全未实现；
  5. R1 刷新（read disturb + retention） —— 不影响毫秒级窗口的带宽/延迟，但决定寿命口径；五个规范空白点的默认选择与验收标准已写成设计输入：docs/survey/refresh-model-design.md；
  6. A6 + A7 AXI user 字段与 per-ID 队列 —— 接口语义完整性，决定 batch hint 能否进来、开环注入是否高估并发。

前四项可以在 HBFSim 上以插件/改造方式加；B1 需要同时动设备映射与主机 FTL（已完成）；R1 要新增 per-block 计数、错误码与主机策略，但没有架构性障碍——读/写路径都是现成的。

6. 能否接入 SystemC 环境

结论：不能"直接接入"，但可以低成本接入 —— 而且比大多数自建方案省力。
HBFSim 自身零 SystemC/TLM 依赖，也没有 TLM socket；但它的物理层是普通 C++ 库（hbfsim_core），且设备模型是"有限资源日历 + 显式时间参数"的对象，不是内建事件循环 —— 这两点决定了它可以被 SystemC 模块包住。

关键事实（为什么可行）

事实证据对 SystemC 接入的含义
无 SystemC 依赖src/、cmake/、CMakeLists.txt 中 systemc / sc_module / sc_core / tlm_* 零命中不会和你的 SystemC 版本冲突，可同进程链接
核心是库不是单体程序cmake/Targets.cmake 定义 hbfsim_core（19 个 .cpp，PUBLIC 暴露 src 头文件）直接 target_link_libraries(your_sc_model hbfsim_core)
设备 API 是"算时间"而非"跑事件"HbfDevice::transfer() 返回 Transfer{start_ns, finish_ns, wait_ns}；read_ready() / complete_program() / cache_hit() / cache_fill() 都是带显式 now_ns 参数天然适合 TLM b_transport 的 annotation 语义，不需要改动它的时间模型
也有进程级协议BEGIN/END/QUIT 行式协议 + JSON 响应（src/app/session_protocol.cpp）不想改 C++ 时，用 subprocess 协同仿真，零侵入
时间基准是 double 纳秒HbfDeviceConfig 全部 *_ns 为 double；引擎内部用 ns需要 sc_time ↔ ns 的双向换算与时间量子约定（见下）

三种接入路径

路径 B 的代码骨架

// 1) CMake：把上游当库链接（不 fork、不改它的源码）
add_subdirectory(third_party/HBFSim)          # 或 find_library(hbfsim_core)
target_link_libraries(your_sc_model PRIVATE hbfsim_core)
target_compile_features(your_sc_model PRIVATE cxx_std_20)

// 2) SystemC 侧：TLM-2.0 target 包住 HbfDevice
struct HbfDeviceTLM : sc_module {
  tlm_utils::simple_target_socket<HbfDeviceTLM> socket;
  hbfsim::physical::hbf::HbfDevice device;      // 纯 C++ 对象，非 sc_module
  static constexpr double NS_PER_PS = 1e-3;

  SC_CTOR(HbfDeviceTLM) : socket("socket"), device(cfg) {
    socket.register_b_transport(this, &HbfDeviceTLM::b_transport);
  }

  void b_transport(tlm::tlm_generic_payload& gp, sc_core::sc_time& delay) {
    const double now_ns  = delay.to_default_time_units();      // 与本模型时间基对齐
    const double pages   = double(gp.get_data_length()) / 4096.0;
    const auto ch = device.channel_for_page(gp.get_address() / 4096);
    const auto t  = device.transfer(ch, Direction::DeviceToHost, gp.get_data_length(),
                                     now_ns, now_ns);          // 返回 start/finish/wait
    delay += sc_core::sc_time(t.finish_ns - now_ns, sc_core::SC_NS);
    gp.set_response_status(tlm::TLM_OK_RESPONSE);
  }
};

接入时必须处理的 4 个细节

问题建议做法
时间基SystemC 用 sc_time（建议 time resolution 设 1 ps），HBFSim 用 double ns。只在边界换算，内部保持各自单位，避免累积舍入。
粒度HBFSim 是页/突发粒度（4 KiB 页、64 B 对齐 burst）。若你的 TLM 是 cache-line 粒度（64 B），有两种选择：上层聚合到 4 KiB（推荐，符合 HBF 语义），或保留 64 B 但按页号聚合 sense。
主机层要不要只做设备性能模型：直接 HbfDevice（无 L2P/GC）。要做端到端：链接 HbfController 或整个 simulation_session，但后者自带事件循环，会和 SystemC 的调度器打架 —— 这时应选路径 A。
因果水位transfer() 与 advance_cache() 带 causal_watermark_ns 参数。SystemC 侧要保证"已提交事务的最小时间"单调推进，否则缓存填充/完成的可见性会不真实。

8.1 地址布局 A/B：顺序物理访问下差 15.8 倍

B1 的动机就是这张表。同一台设备（1 通道 × 1 die × 16 bank，tR = 4 µs，4 KiB 页），把 256 个连续物理页一次性下发，只切换通道内的地址布局：

布局256 页顺序读每通道有效带宽解析预期顺序写（同样 256 页）
bank-major（模型默认）1024.4 µs1.02 GB/s256 × tR = 1024 µs51.2 ms
ocp_v070（p.22 位序）65.0 µs16.13 GB/s16 × tR = 64 µs3.2 ms

读数与解析式逐项吻合：bank-major 下 256 页全落在同一个 bank（16 blocks × 16 pages = 256 页/plane），只能串行 256 次 sense；ocp_v070 把它们均摊到 16 个 bank，每个 bank 16 次。写同样吻合：bank-major 需 16 次块擦除串行（16 × 2 ms）+ 256 次 program（256 × 75 µs）≈ 51.2 ms，ocp_v070 的 16 次擦除在 16 个 bank 上并行、program 也并行，约 2 ms + 1.2 ms ≈ 3.2 ms。

但逻辑流量看不出差别：512 个顺序 4 KiB 逻辑读、每 1 µs 一发，两种布局都是 515.5 µs / 4.07 GB/s——主机 FTL 已经把 LPN 打散到各 plane。结论：布局影响的是物理/旁路访问，以及主机映射不做 striping 时的排布；这也是把 ocp-v070 做成可选 overlay、而不是直接改默认值的原因。

D6 诊断顺带修掉一个 OCP 路径的 bug：擦除/GC 回收/device-DRAM 清理这三处仍按 block × pages_per_block + page 线性遍历块内页，在 ocp_v070 下 16 个块的擦除全部解到同一个 plane，被串行成 16 × 2 ms，写因此假性慢到 33.2 ms。改成按布局编码后回到 3.2 ms——换布局必须把所有"块内页连续"的假设一起排查，否则会得到假的性能结论。

同一类假设在 GC / 磨损均衡里还有第二处：relocate_live_pages 与回收校验都用 block_begin + page 找块内页，在 ocp_v070 下重定位会读写错页，回收提交时直接报 “GC source page table remained live at reclaim commit”。已一并改为按布局编码，并新增 hbf_gc_layout 测试：回退修复该测试失败、恢复修复后通过，两层验证都留在了仓库里。

复现：物理访问需要先声明 extent（static_hbf_blocks_per_plane=0、published_hbf_blocks_per_plane=16），脚本见仓库 docs/survey/ab_layout_physical.py。

9. 外部 → HBF 的三条路径

模型里"外部到 HBF"有三条可测量路径，区别不在物理路线，而在一条 session 事务计了哪几段：每条事务只负责一个阶段，端到端必须用 dependencies 串联。

路径事务计入实测（fork feat/ocp-v070-gaps）回答的问题
A 主机 → HBF HBF_LOGICAL / HBF_PHYSICAL HBIO 接口 + TSV/ECC/SRAM + NAND 阵列（逻辑路径再加 FTL/GC） 48 / 96 GB/s·通道；冷读 4.44–4.51 µs；命中 131–196 ns 设备整体对外带宽
B 外部 → 直连 lane DIRECT_EXTERNAL_TO_HBF（op=W） 只有 lane 传输段（32 GB/s · 100 ns） 31.9 GB/s（256 页） 封装外链路够不够快
C 端到端链 EXTERNAL R → DIRECT W → HBF_PHYSICAL W 外部设备 + lane + HBF program/erase 0.744 GB/s（预擦除）

读图结论：B 与 C 走的是同一条物理 lane，差别只在事务覆盖面；A 计满设备内部，测的是设备接口能力。数值相差两个数量级（链路 32 GB/s 对端到端 0.1–0.7 GB/s），说明瓶颈在 NAND 的 program/erase，而不在封装外链路——这与 HBF"读快写慢"的定位一致。

复现脚本随文档放在 docs/survey/：fork_evidence.py（路径 A）、ext_lane.py（路径 B）、ext_to_hbf_chain.py（路径 C）。B/C 路径需要 hbf-external-direct-link-enable=true 与 enable_external=True；C 还要求物理写所需的 published extent。

9.1 A 与 C 的关系：同一段落盘路径的两个入口

把 C 拆开量一次，可以直接看到"差不多"的来源（预擦除块、单通道 16 plane、ocp 布局）：

阶段64 页256 页说明
① 外部设备读（EXTERNAL）81.6 µs / 3.21 GB/s201.6 µs / 5.20 GB/s外部设备固定延迟 + 队列，页数少时占比大
② 直连 lane8.3 µs / 31.61 GB/s32.9 µs / 31.90 GB/s接近配置的 32 GB/s
③ HBF 物理写（= A 的写方向）301.0 µs / 0.87 GB/s1201.0 µs / 0.87 GB/sprogram 75 µs/页 ÷ 16 plane
C 端到端352.3 µs / 0.74 GB/s1252.3 µs / 0.84 GB/s③ 占 C 的 85.4%（64 页）/95.9%（256 页）

所以"C 与 A 的 program 带宽看起来差不多"不是巧合：C 的带宽被 ③ 支配，① 只在页数少时占一成多，② 几乎可以忽略。想提升恢复/迁移带宽，优化外部设备或 lane 的收益很小，真正的杠杆在 ③——更多 plane/die 提高 program 并行、cache program，或降低 tPROG。

A 和 C 不是两条并列的路，而是"共享后半段"的两条入口：

  • A 是主机的正常访存——入口是 UCIe/AXI（HBIO），读和写都走它；
  • C 是把外部 tier 的数据恢复进 HBF——入口是封装外的直连 lane，只有写方向；
  • 两条路的后半段完全重合：Base die → NAND program/erase。C 的第 ③ 段就是 A 的写方向，模型里它确实是一条 A 类型的事务（HBF_PHYSICAL 写）。

数值上的印证：C 的端到端带宽（0.744 GB/s，预擦除）几乎等于 A 写方向的极限，说明前两段（外部设备读、lane 32 GB/s）都不是瓶颈；而 A 的读方向不经过 program，所以能跑到 48/96 GB/s·通道。一句话：A 是"营业窗口"，C 是"补货通道"——补货再快也得按"上架"速度算，而"上架"和客人存东西是同一条流水线。
